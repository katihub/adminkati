# Product delivery interval

## Requirement

The client wants each product to carry a delivery interval. Every product defaults to **30 min – 72 h**.
Admins can instead pick **5 working days, 10 working days, 2 weeks, 1 month, 3 months**, and can
**add more options** to the list. Options are stored in the backend, so this is end to end:
`NowTech-backend-` plus this admin panel.

The backend lives at `/Users/michaelnji/Projects/nvc/NowTech-backend-` (NestJS + Prisma + raw SQL,
branch `development`). The user granted explicit rights to work there for this feature. It was read
on 2026-09-30 and the plan below is reconciled against it; see **Backend reconciliation**.

## Backend reconciliation (read from `NowTech-backend-`, 2026-09-30)

Three findings change the mechanics, not the decisions:

1. **`nowtech.produits` is a regenerated schema.** `scripts/ingerer-catalogue.mjs:233-261` builds
   `nowtech_prep`, renames it over `nowtech` and drops the old one. A `delai_livraison_id` column on
   `nowtech.produits` would be wiped by every ingestion, and `sql/*.sql` only replays columns, not
   data. Precedent: `ProductCost` (`prisma/schema.prisma:78-90`) is a Prisma table in the public
   schema, keyed by `product_id`, **with deliberately no FK to `nowtech.produits`**.
   **Consequence:** decision 2 keeps its behaviour (no row = inherit the default) but is stored as an
   assignment table, not a nullable column on the product.
2. **Writes are `direction` only.** `administration.controller.ts:72,83` lets `direction` and
   `comptoir` read; every product write is `@Roles(Role.direction)`. New writes follow that, and
   `comptoir` gets read on the options list (the picker needs it on a read-only product view).
3. **Every write is journaled** (`JournalService.consigner`, see `couts.service.ts:50-62`) with the
   caller's name taken from the token, never the body. Option create/edit/archive and per-product
   assignment must do the same, especially default-inheritance changes.

Conventions to follow: French domain names, French block comments, DTOs with `class-validator` in
`administration.dto.ts` style, service specs beside the service (`couts.service.spec.ts`), Prisma
migration in `prisma/migrations/<ts>_<name>/migration.sql`, `pnpm test` (jest, ESM VM modules) and
`pnpm lint`. Admin-side code comments stay English (repo rule); backend comments stay French.

## Decisions (resolved via grilling, 2026-09-30)

### Backend

1. **Option shape**: structured. `min_valeur`, `max_valeur` (null = single value), `unite`
   (`minutes | heures | jours_ouvres | jours | semaines | mois`). No stored label; the label is
   generated per locale by the frontend.
2. **Default**: a product with no assignment inherits the option flagged `est_defaut`. Changing the
   default needs no backfill. Seed 30min–72h as the default plus the five client options. Stored as
   table `product_delivery_intervals(product_id PK, interval_id FK)` in the Prisma schema, not as a
   column on `nowtech.produits` (regenerated by ingestion, see Backend reconciliation). Wire shape is
   unchanged: `delai_livraison_id: number | null`, where null deletes the assignment row.
3. **Lifecycle**: create, edit, archive (`actif = false`). No hard delete. The default option cannot
   be archived. `min_valeur`, `max_valeur` and `unite` are immutable once any product uses the option,
   so a promise already shown to customers is never silently rewritten.
4. **API**: own resource `/catalogue/administration/delais-livraison` (list, create, patch/archive).
   Product create/patch accepts `delai_livraison_id` (null = default). Product detail embeds the
   resolved option. Same role guard as product edit.
5. **Consumers**: the public catalogue returns the resolved option (default applied), display only.
   Orders do not snapshot it in this phase.

### Admin panel

6. **Placement**: new `OverviewDelivery.vue` in the Overview Details column, beside the stock toggle.
   Shared by add and edit, disabled when `!canWrite`.
7. **Add**: combobox with an "+ Add option" footer that opens a create dialog. The created option is
   auto-selected on the product.
8. **Manage**: ONE manage dialog, opened by an icon-only trigger placed next to the add button. It
   lists all options and supports edit and archive. (Restore of an archived option is included
   because the backend model is a flag flip; see Open questions.)
9. **Dialog fields**: unit select, an "Exactly / Between" toggle (one number or min + max), live
   localized label preview. Zod schema in `app/schemas/`.
10. **Default and state**: a null product value shows the default option with a "Default" badge;
    picking the default sends null. Options come from TanStack Query and are invalidated on every
    mutation. A fetch failure shows `InlineStateNotice`.

## Data contracts

Backend (to be created, in `NowTech-backend-`):

```ts
type DelaiUnite = "minutes" | "heures" | "jours_ouvres" | "jours" | "semaines" | "mois"

interface DelaiLivraison {
  id: number
  min_valeur: number        // > 0
  max_valeur: number | null // null = single value; if set, >= min_valeur
  unite: DelaiUnite
  est_defaut: boolean
  actif: boolean
  utilise_par: number       // product count, drives immutability and the UI's "in use" hint
}
```

| Endpoint | Body | Notes |
| :-- | :-- | :-- |
| `GET  /catalogue/administration/delais-livraison` | none | all options including archived, default first, then by approximate duration |
| `POST /catalogue/administration/delais-livraison` | `{ min_valeur, max_valeur, unite }` | 409 on duplicate (same min/max/unite) |
| `PATCH /catalogue/administration/delais-livraison/:id` | `{ min_valeur?, max_valeur?, unite?, actif? }` | 409 if changing value fields while `utilise_par > 0`; 409 archiving the default |
| product create / `PATCH .../produits/:id` | adds `delai_livraison_id?: number \| null` | null = inherit default |
| product detail | adds `delai_livraison: DelaiLivraison` (resolved, default applied) plus `delai_livraison_id: number \| null` (the raw stored value, so the admin can tell "inherits" from "explicit") | |
| public product | adds resolved `delai_livraison` | display only |

Admin side (to be created): `app/types/api/delais-livraison.ts` with the interface above and
`ProductDetail.delai_livraison_id` / `delai_livraison` added to `app/types/api/produits.ts`.

Migration `prisma/migrations/<ts>_delais_livraison/migration.sql` (Prisma models `DelaiLivraison` →
`delais_livraison`, `ProduitDelaiLivraison` → `produit_delais_livraison`): the options table, the
assignment table (`product_id` unique, FK to the option, **no FK to `nowtech.produits`**), seed six
rows with 30min–72h flagged `est_defaut`. Enforce a single default with a partial unique index on
`est_defaut WHERE est_defaut`, and a check that `max_valeur IS NULL OR max_valeur >= min_valeur`.
Endpoint-level rename: `delai_livraison_id` on the product contract is served from the assignment
table by `lireProduit` (`administration.service.ts:210`) and written by `creerProduit` /
`modifierProduit` (`:268`, `:300`) inside the same journaled flow.

## Risks

- **Product ids across ingestion.** The assignment table keys on `product_id` with no FK, exactly like `product_costs`. If an ingestion ever renumbers products, assignments silently attach to the wrong product. Same accepted risk the costs feature already carries; Phase 1 should confirm ids are stable (they come from the source catalogue) and a withdrawn product's assignment is simply ignored.
- **Orphaned assignments.** With no FK, a deleted product leaves a row behind. Harmless (never read), but the "in use" count must join against live products or it overstates usage and blocks edits needlessly.
- **Business days.** `jours_ouvres` needs a holiday/working-week rule only if an ETA is ever computed. Display-only this phase, so no calendar logic; flagged so nobody adds ETA math without one.
- **Immutability vs. typo.** A wrong value in an option already in use cannot be fixed, only archived and recreated. Accepted trade-off; the manage dialog explains it when fields are locked.
- **Public projection change** is visible to the storefront immediately; storefront must tolerate the new field being absent during a staggered deploy.
- **Shared-default drift.** Because null inherits, moving the default changes what every untouched product promises. The backend should log default changes; UI confirms before moving the default flag (if a "make default" action is exposed, see Open questions).
- **10 req/s backend throttle.** The options list is one extra query on the product page; fetch it lazily when the product form mounts, not as an SSR prefetch (not above the fold).

## Open questions

1. **Can admins change which option is the default?** Not decided in the grilling. Without it the default is fixed at seed time. Recommendation: not in this phase; add later once the client asks. The `est_defaut` column and inheritance already support it.
2. **Restore archived options?** Assumed yes in the manage dialog (a flag flip). Recommendation: keep.
3. **Max value cap.** Assumed 1..999 per number, to be confirmed against client language such as "3 months" vs "90 days". Recommendation: cap at 999.
4. **Display order.** Assumed by approximate duration, computed on the backend from a per-unit weight, default first. Alternative: manual ordering. Recommendation: by duration.
5. **Deploy order.** Backend must ship before the admin change; the admin picker degrades to `InlineStateNotice` if the endpoint 404s, so an early admin deploy is safe but useless.
