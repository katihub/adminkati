# Plan : l'espace Audit

## Besoin (décidé le 12 novembre 2026)

Un espace **Audit** dans l'admin pour savoir **qui a fait quoi, et quand**. Décisions :

- **la direction seule** le voit (ni le futur gestionnaire KatiMarket, ni aucun autre rôle) ;
- les **adresses IP** sont affichées ;
- on ne trace pas les consultations inutiles ; seulement quelques-unes, quand elles le méritent.

## Source

Le journal (`boutique.journal`) enregistre déjà les actions : commandes, paiements, retraits, dossiers vendeurs, catalogue, équipe… avec l'auteur, son rôle, la date, l'objet, l'adresse IP, l'agent et le détail. Le rôle applicatif ne peut ni modifier ni effacer une ligne. Aucun écran ne le montrait.

## Règles

- **Liste** paginée (50 par page), la plus récente d'abord : date, action, auteur (nom du membre, du vendeur et de sa boutique, ou adresse du client), rôle, objet, adresse IP.
- **Filtres** : période (jours, heure de Douala), famille (argent, commandes, vendeurs, catalogue, clients, administration), type d'auteur, membre de l'équipe, identifiant d'un objet, morceau du code d'action.
- **Détail** d'une ligne : motif, agent, détail complet.
- **Export CSV** de la sélection, 10 000 lignes au plus, sans formule possible dans les cellules.

## Consultations tracées en plus

- `audit.exporte` : l'export de l'audit, avec ses filtres et le nombre de lignes ;
- `vendeur.document.consulte` : un membre de l'équipe ouvre une pièce d'un vendeur (identité, RIB…).

Les consultations déjà tracées restent (fiche client, finances d'une boutique…). Ouvrir l'écran d'audit ne laisse pas de trace.

## Étapes

1. **Backend** : module `audit` (`GET /v1/audit`, `GET /v1/audit/export`, direction seule), trace des pièces consultées. Tests Jest.
2. **Panel** : page `/audit` (direction), entrée **Audit** dans Administration, filtres, liste, détail, export. Tests Vitest.
